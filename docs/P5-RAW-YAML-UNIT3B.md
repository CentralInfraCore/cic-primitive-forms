# P5-3: raw YAML and the parser boundary, Unit 3b (dump and compare): what it is and what the first run measured

Status: **implemented in this change**, 2026-11-05, local only. It follows `docs/P5-RAW-YAML-UNIT3-CONTRACT.md` (#158) on the cases of Unit 3a (#159). It is the dump and compare half of the proof: **the selftest and the evidence report (Unit 3c) are on hold**, so nothing here is evidence, and `report.json` says so (`evidence: false`). `P_effective` below is an analysis result, not a production admission: decision D9 (how production enforces `P_allowed`) is not made. No workflow file changes; the production receipt API stays on hold.

## What runs

```
python3 tools/parity/run_raw_yaml.py [--out DIR]        # needs go, cargo, python3 with PyYAML
```

The same 2223 byte-level cases (hex, so invalid UTF-8, a BOM and control characters reach every reader unchanged) are given to three readers: the Rust `parse` and `map_release` (`rust/tests/parity_raw_yaml_dump.rs`), the Go `Parse` and `MapRelease` (`go/parity_raw_yaml_dump_test.go`), and PyYAML `safe_load` with the Unit 2 mapping reference (`tools/parity/dump_raw_yaml_py.py`, the oracle of difference, never a vote). `tools/parity/compare_raw_yaml.py` asks five separate questions per case: **parity** (Rust and Go both accept with the same tree: measured from the two answers, never taken from a label), **construction** (the outcome fixed by the case), **allowed** (the normative label; `P_effective` = parity and allowed), **mapping** (both parsers' mapping answers equal `mapping_expect`), **python** (PyYAML against the admitted tree on the members the mapping reads). The fail-closed rules of the contract (unknown, missing, duplicate, reordered ids; unfinished last line; CRASH and TIMEOUT; thin class; a pinned divergence in `P_parity`; a pinned divergence that no longer diverges, as its own event; a forbidden construct in `P_parity`; a blocking Python difference; a vanished known difference) each make the run red. `tools/parity/test_compare_raw_yaml.py` (12 tests) keeps the comparison honest on synthetic dumps; it is not the Unit 3c selftest.

**The limits are enforced as execution limits, not only reported.** Every reader is a separate process, started under `RLIMIT_AS` (6 GiB) and writing one line per case as it goes. The runner **supervises** it: when a case takes longer than the limit (10 s; 5 s of start-up grace for the first case of a start) the runner **kills the whole process group** and writes `TIMEOUT` for that case; a case that kills its process (the memory limit, a crash, a panic) is written `CRASH`; in both cases the run restarts after it with a fresh process. No timer runs inside the readers, so an overrun case never goes on working in the background and cannot take CPU or memory from the next one. `tools/parity/test_run_raw_yaml.py` shows this with a stand-in reader that allocates past the limit and one that never answers: both are recorded, the rest kept, and the stuck process is gone afterwards. The Forms parsers take text, so a byte sequence that is not UTF-8 is answered `invalid_utf8` by the dump before the parser is called; the production API will have to decide that itself.

**Semantic and position parity are apart (decision D10).** The dumps also write the source position of every node and key and the location of every refusal. `P_parity` is semantic; position parity is measured separately, and the pinned divergences that differ only in positions are subtyped and declared with their original answers (`tools/parity/pinned_subtypes_raw_yaml.json`, written by `tools/parity/make_raw_yaml_expectations.py` from a measured run). **Known differences are per case id with exact answers** (Rust and Go refusal classes, a hash of PyYAML's tree) and a recorded acceptance (`known_differences_raw_yaml.json`, 67 entries): no class prefix, and a case of the same class is not blessed by its neighbour.

## First run after the review of #160 (local; go 1.25.0, rustc 1.99.1, python 3.12.3, PyYAML 6.0.1; 2223 cases; input SHA-256 `574538c0…1eebe`)

Measured: **2222 green, 1 red.** No reader crashed; the Go reader was killed once, on the case below.

| # | Finding | Facts |
|---|---|---|
| F1 | **Go parses a long flow sequence in quadratic time; the node limit is reported only after ~19 s on a 300 KB input** | `limit-over:nodes`: a flow sequence of 150 000 items (300 662 bytes). Rust refuses it with the node limit in time; Go answers `LIMIT_EXCEEDED` only after **18.9 s** (about 50 MB resident), so the runner kills it at 10 s and records `TIMEOUT`. A scaling run of the Go `Parse` (`wide: [0,0,...]`): 10 000 items 0.20 s, 20 000 0.76 s, 40 000 3.04 s, 80 000 12.16 s, 99 000 18.39 s: doubling the items multiplies the time by about four, so **an input inside every documented limit (160 KB, 80 000 items) already takes 12 s**. Tracked in issue #161 with its acceptance criteria (early detection of the limit, no superlinear growth over several sizes and shapes, the Rust parser measured the same way). It stays red until a fix, or a separately approved limit, is proven. |

The first run before the review had five more red cases: the five pinned divergences whose Rust and Go answers differ only in source positions (four accepted inputs with the same tree, one duplicate-key refusal at another location). Under D10 they are subtyped (`positions_only` x4, `refusal_position_only` x1) and stay in the report with stable ids and their original answers; the run checks them on every run.

Measured, not red:

* **Construction and mapping hold where promised.** All 480 `built` (12 styles of valid records), 1068 `tree` and 34 `value` cases: both parsers accept, same tree, the constructed tree, and the mapping answers equal the Unit 1/2 yardstick (including `"3"`, `null` and a block-scalar digest, which are accepted texts the mapping refuses). Every forbidden construct of the catalogue (duplicate keys in 3 spellings at every level, in block and flow style, anchors, aliases, tags, merge keys, tab, control characters, directives, second document, floats, hex, octal, leading zero, 64-bit overflow, the clear limit overruns except F1) is refused by **both** parsers in the stated class; no forbidden construct is in `P_parity`.
* **`P_effective`: 1584** (analysis only). 294 of the 299 pinned occurrences still diverge semantically between Rust and Go (253 accept against refuse, 23 different trees, 18 different refusal classes); 4 are `positions_only` and 1 is `refusal_position_only`; 201 distinct inputs behind the 299 occurrences.
* **Undetermined constructions in `P_parity`: 19 of 24.** Both parsers accept a missing final newline, CRLF, a lone CR, a leading BOM, an NBSP and a zero-width character in a comment, an empty document, a comment-only document, `null`/`yes`/`no`/`on`/`off`/`y`/`n` as the envelope, and a text of exactly 1 MiB. They are not `allowed`, so not in `P_effective`; the owner's classification (D3) decides each.
* **PyYAML.** Accepts what both Forms parsers refuse, in the safe direction: all 42 `dup`, 24 `dup-flow` and 1 `dup-unread` cases (the known difference: PyYAML takes the last of two equal keys; each of the 67 per-case entries is satisfied with its exact answers and the run goes red if one stops occurring or changes), and also 66 pairs, 26 scalar spellings, 15 injected members, 84 float records, 6 text defects, 2 limit overruns. On 6 undetermined cases PyYAML reads the envelope `yes`, `no`, `on`, `off` as a boolean where both Forms parsers read a string: **a difference on a member the mapping reads, on an input that is both parsers' parity but not allowed, so not admitted**. If D3 ever classifies those spellings as allowed, this becomes a blocking difference. No admitted input differs from PyYAML on a member the mapping reads.
